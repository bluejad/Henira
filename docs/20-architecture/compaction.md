### 1.2 四家一致、本仓直接采用的做法

1. 每一步请求前都检查，不是每个回合才检查（一个工具结果就能涨几万 token）。
2. 阈值按**即将请求的模型**的窗口算——换模型降档因此天然被覆盖，不需要专门分支。
3. 计量以厂商返回的 usage 为锚点，只估算锚点之后的增量。
4. 摘要请求与主循环同系统提示、同工具表、同 `tool_choice`、同思考参数、同会话头，消息取主请求的前缀；能整段带上就带（同形），装不下就只带头部——尾部不被遮蔽、也不进摘要（§4.6）。ZCode 常规摘要送的同样是选中区间的头部前缀，理由写在它的缓存注释里 [zcode] `apps/zcode-cli/packages/core/src/runtime/methods/compact-active.ts:283-286`。
5. 工具调用与其结果永不拆开；系统提示永不进替换区间。
6. 摘要请求自身装不下时，缩小的是「喂给摘要的转写」，不是会话；最新的内容只缩不丢；缩到头明确失败。三家公开参照都自己收缩（OpenCode 四档、ZCode 重选区间 + 截断、闭源产品丢最老轮次）；dsh 把这一步留给恢复钩子、默认重抛 [dsh] `packages/compaction/compaction-basic/src/region.ts:397-409`，本仓照前三家做。
7. 溢出后压缩失败，上报的是**原始的溢出错误**。
8. 连续失败有熔断，会话不空转。
9. 用户看到的历史不消失，压缩处有可见边界。

### 3.2 真 key 采样结论（2026-11-26，DeepSeek / 智谱 / Agnes / OpenCode Go 四端点）

脚本不入库；密钥经官方配置口子取、只进请求头。

**usage 口径（定案）**

- 四端点的 `prompt_tokens` 都是**输入总数**，`prompt_tokens_details.cached_tokens` 是它的子集。所以账本里的 `inputTokens` 就是完整的 prompt 大小，计量锚点成立。
- 网关在 `opencode.tokens.input` 里只算未命中的部分（总数 6734 时它是 78）。读错字段会低估近百倍。
- 四端点都有自动前缀缓存，命中粒度 64 token。

**摘要请求形状（定案）**

- **工具表必须随请求发出，且 `tool_choice` 保持 `auto`。** 设成 `none` 时，DeepSeek、Agnes、网关把工具表踢出提示词（约 350 token 不再计入），缓存全部未命中；智谱工具表照算，但**无视 `none`，照样发起工具调用**。
- **思考参数必须与主循环一致。** DeepSeek 开思考比关思考多 26 个 token 的提示词，切换即缓存全部未命中；智谱同样；Agnes 切换后缓存仍在。
- **缓存命中不是保证。** DeepSeek、Agnes 同形必中；智谱与网关存在同形请求漏命中、且位置可复现。对齐前缀是必要条件，不是充分条件——设计只能把它当省钱的收益，不能当依赖。
- 不发思考参数时 DeepSeek、智谱、网关默认开着思考，思考 token 计入 `max_tokens`：一条「hi」配 `max_tokens: 8`，8 个全是思考，正文为空。**摘要的输出上限必须留足思考余量，「length 结束且正文为空」是真实的失败形态。**
- 代码注释里「带 tool_calls 的历史不回传 reasoning_content 会 400」在这代端点没有复现（与 50-open.md 2026-11-19 的记录一致），注释过时，本批更正。

直接影响设计的结论：

1. **静默截断的端点上，「溢出报错触发压缩」这条路走不到。** 只有请求前的压力检查能保护会话（I-13）。字典给的窗口还可能高于实际上限：截断读数 196608 比该模型字典窗口（256000）的压力线还低，压力检查按字典算永远不触发——所以还要能从读数里把实际上限学出来（§4.2）。
2. **分类器只能照自己端点的真实报错来建，而且排除项要先于匹配。** 把采样到的原文拿去对四家的识别规则：智谱与网关的措辞只有 OpenCode 的清单认得，dsh 要求「超出」的对象明确写着 context，ZCode 与闭源产品都对不上；反过来 OpenCode 的清单里有 `exceeds the limit of \d+`，会把 Agnes 的第③类原句判成溢出。压缩救不了 `max_tokens` 参数错——借来的清单两头都会错。
3. **报错原文带精确读数与上限**（DeepSeek 的消息数、Agnes 的输入数、网关的请求数；三家都带窗口上限）。回灌给计量器与观测上限（§4.2、F-1），是不花钱的精确锚点。
4. **第②类与第①类是同一句话**：端点把 `max_tokens` 计入窗口。主请求的输出封顶（§4.3）因此不是省钱措施，是让请求装得下的必要条件（I-14）。

**另外三种请求形状（同日晚）**

- **相邻两条 user**（摘要指令紧跟在用户消息之后）+ 工具表 + `tool_choice: auto`：四端点全部接受（200）。
- **输出封顶**：`max_tokens: 30` 配要求长答案，四端点都是 200 + `finish_reason: length` + completion 正好 30。开思考的三家（DeepSeek、智谱、网关）这 30 个 token 全是思考 token、**正文为空**——封顶值小时，思考模型会给用户一个空回复（F-14）。
- **适配器边界**：四端的溢出与参数错都经 AI SDK 的 `APICallError` 到达，`statusCode`、`message`、`responseBody`（原始响应体文本）、`data`（已解析的响应体）、`isRetryable` 都在上面；现在的转换只取了 `message`。

## 4. 设计

### 4.1 组件与装配

新包 `plugins/compaction`（`@henira/plugin-compaction`），占 `compaction` 槽，注入 `session` / `llm` / `tools` / `config` / `loop`。进 `defaultPreset`，属外圈官方件（可停用）。

内部按职责分文件，一个文件一个说得清的职责：选区（selection）、摘要请求（summarizer）、落账（writer）、熔断（breaker）、手动入口（service）。溢出错误码的判定表住 `plugin-llm`，本插件只消费错误码；计量与阈值公式也不在本插件（见下）。

挂载点：

- **`loop/pre-step`（waterfall，本批由 loop 落地派发）**：在 `runStep` 内、派生之后 `request/header` 之前派发（回合主循环与熔断续跑两条路径都经过），插话已在此前落账；本插件在其中做压力检查与压缩，并把压缩后重新派生的 `messages` 交还给瀑布流。既定载荷只有 `messages` 与 `tools`，本批补 `model` / `reasoningEffort` / `sessionId` / `turn` / `step` / `context`（计量器读数：已用、上限、压力线、硬线、是否估算）（§4.12）。
- **`loop/request-failed`（waterfall，本批新增的缝）**：请求失败后派发，载荷含类型化错误与已重试次数；监听器可以返回 `{retry: true}` 表示「已处理，请原步重发」。
- **总线 `compaction/applied`（serial）**：替换落账之后广播，供将来持有持久状态的插件重注入（session.md §4 既定）。

**计量器不放在本插件里，放在 loop**（第二轮修订）：谁发请求，谁保证请求装得下（I-14）；主请求的输出封顶要用读数；本插件停用时封顶与余量显示照常成立。估算函数与阈值公式住 protocol（纯函数、零依赖），loop 与本插件共用同一份——两处各算一套常量，正是 [zcode] `apps/zcode-cli/packages/core/src/compact/policy.ts:6-14` 的注释警告的事。宿主从 `LoopService.contextUsage()` 并入余量活态，与队列活态同一出口。

### 4.2 计量器

```
锚点     = 最近一条 inputTokens 为正的 step/end
           { headerSeq, assistantSeq, input, output, reasoning, echo, model, cacheRead? }
           （出错与中断的步 usage 记 0，不作锚点；原步重发会有两条 request/header，取最后一条）
携带量   = 锚点.output − (echo ? 0 : 锚点.reasoning)     // 不回传的思考 token 不在下一条 prompt 里
           锚点步没有落 assistant/message（被掐）→ 携带量记 0，锚后从 request/header 起算
表面     = session.deriveSurface()                        // 与 deriveMessages() 同一份折叠，每条带 seq（I-1）
当前用量 = 锚点.input + 携带量 + k × estimate(表面里 seq 大于锚点 assistantSeq 的消息)
estimate = Σ estText(文本) + 每条消息 40
estText  = 字母 × 0.5 + 数字 × 1.4 + 标点 × 0.2 + 空白 × 0 + 中日韩 × 1.0     // 按码点计
```

- **换模型即作废锚点**：锚点带着产出它的模型；即将请求的（厂商，模型）与锚点不同，这一次按无锚点全量估算——分词器变了，旧读数不再可比。参照实现同样只在「模型、变体、agent 都没变」时信任实测读数 [opencode] `packages/core/src/session/compaction.ts:1188-1210`；溢出路径上做摘要时干脆不用实测读数 [opencode] `packages/core/src/session/compaction.ts:493`。
- **模型写出来的文本不用估算**：上一步的输出由 `outputTokens` 精确给出。需要估算的只有工具结果、用户输入，以及没有 usage 的中间步留下的消息。
- **缓存命中率只用于显示**：`cacheHitRate = 锚点.cacheRead ÷ 锚点.input`；`cacheRead` 缺省（端点不报缓存）或 `input` 为 0 时不带这个字段。它不进计量——命中与否不改变 `inputTokens` 已是精确读数。
- **五类计价，数字最贵**（真实账本定标，2026-11-26）。参照实现的估算系数是英文经验值（dsh 定为 4 个字符一个 token [dsh] `packages/llm/token-meter/src/estimate.ts:13`；ZCode 按字符数除以一个固定除数 [zcode] `apps/zcode-cli/packages/core/src/compact/manual.ts:116`）。用 93 份真实账本回放（1066 个有 usage 的步、934 对相邻可比步），在「锚后只有工具结果」的干净步上按字符类别回归，三家的拟合优度都在 0.98 以上。每个字符的 token 数：

  | 字符类别 | Agnes | DeepSeek | 智谱 | 取值 |
  | -------- | ----- | -------- | ---- | ---- |
  | 字母     | 0.36  | 0.46     | 0.64 | 0.5  |
  | 数字     | 1.40  | 1.88     | 1.35 | 1.4  |
  | 标点     | 0.22  | 0.22     | 0    | 0.2  |
  | 空白     | 0     | 0        | 0    | 0    |
  | 中日韩   | 0.83  | 0.76     | 1.16 | 1.0  |

  数字接近逐位计价：十六进制转储、ID、表格这类内容比英文散文贵三倍以上。「取值」一列是留了余量的安全值，按它回放全部 934 对：**估算不低于实际的步占 97.8%**（增量 2000 token 以上的步 95.2%；三家分别是 98.1% / 94.9% / 99.3%），**中位高估 21%**，满足本节的两条指标。首稿的两类估算（其余字符 0.4、中日韩 0.8、每条 8）覆盖率只有 59.4%。
- **会话自校正只往安全方向调**：`k` 初值 1。每拿到一个新锚点，若两步之间表面只增不减、模型没有更换、锚后估算不少于 500 token，就比较「实际增量 ÷ 估算」；大于 1（估低了）才纳入，指数滑动（权重 0.3），钳在 1.0–1.5。估高了不下调：内容类别已经由五类系数承担，下调换来的精确不值得冒欠估的险。首稿写的是双向 0.8–1.5，定标后改单向。两步之间有替换落账或换了模型时读数不可比，这一次不更新 `k`。
- **推理回传与否从账本读**：`request/header.params` 记下本步是否回传推理（适配器按「本次思考档 + 模型的 interleaved 声明」现算，两边用同一个判定函数）。真实账本里有 13% 的相邻步「下一条 prompt 的增量比上一步输出还少 50 token 以上」，集中在推理不回传的模型上——上一步输出不能原样当作带进下一条 prompt 的量。
- **无锚点**（会话首个请求、替换刚落账之后、换了模型之后）：全量估算 = 系统提示 + 工具表 + 全部消息，只用一步。工具表按「名称 + 描述 + 入参 schema」序列化后的文本估，每个工具另加固定开销；真实账本里首个请求的实测是 7 个工具约 1150 token、8 个工具约 1450 token（系统提示加首条消息只占一百多），工具表是全量估算里的大头。
- **已知盲区**：工具表在两步之间变化（MCP 异步接入）时，读数要到下一个锚点才反映；93 份真实账本里没有出现。真发生了，由溢出报错（F-1）或截断嫌疑兜住。
- **溢出报错回灌**：溢出报错里解析出的实际输入数是当前表面的精确读数——拿到就把它当作该表面的用量，估低了多少按同一规则上调 `k`；解析出的上限低于字典窗口时按观测上限处理。
- **截断嫌疑**（I-13 的落地）。有锚点、且两步之间表面只增不减、模型没有更换时，比较两个增量：预期增量 = 上一步携带量 + 锚后事件的估算；实际增量 = 本步 `inputTokens` − 上一步 `inputTokens`。
  - **嫌疑读数**（满足任一条）：① 锚后新增内容的估算不少于 200 token，而读数增长不超过 64——读数纹丝不动；② 预期增量不少于 2 千，而实际增量不足它的一半——增长明显跟不上。单次嫌疑只上屏提示（「厂商报告的用量比预期少 N」），不学上限，也不进 `k` 的更新（它偏低不是估算器不准）。
  - **确认**：连续两次嫌疑读数，且两次读数相差不超过 64 token——就是被截到了硬顶。确认后把这个读数学成该（厂商，模型）的**观测上限**，之后阈值取 `min(字典窗口, 观测上限)`。要连续两次且读数持平，是因为单次读数偏低也可能只是估算器失准，学错的上限会把压力线压到会话越不过去的地方。
  - 观测上限记在进程内存里（按厂商 + 模型），重启后重新学；要长期生效就在 `models.json` 里覆盖窗口（§8）。
  - 采样到的那个端点正是这种形态：两次大小不同的超限请求返回同一个读数（§3.2）。只看「增长跟不上」抓不全它——预期 22 万时，被截到的 196608 是预期量的 89%；而截断之后每一步的读数都不再动，后面每步只涨几百 token 的会话靠的正是第 ① 条。
  - 这是本仓自己的发明，参照实现里没有对应物（它们没有遇到会静默截断的端点）。

### 4.3 阈值与预算

```
window     = ModelConfig.contextWindow，缺省 128_000（已取，§8）
上限       = min(window, 观测上限)
reserve    = clamp(floor(上限 × 0.15), min(8_000, floor(上限 / 4)), 64_000)     // 输出 + 估算误差
pressure   = 上限 − reserve     // 到达即压缩
hardLimit  = 上限 − 1_000       // 用量到达此线不发请求（I-13）；这 1_000 是输出余量的下限
outputBase = min(ModelConfig.maxOutputTokens ?? 32_000, 观测输出上限)   // 观测输出上限来自第③类报错（见下）
summaryOut = min(20_000, reserve − 2_000)            // 摘要的输出预算；2 千 = 摘要指令 + 余量
```

- 阈值按**即将请求的模型**算，换模型降档自然被覆盖。
- **输出预算必须是一个已知数**（I-14）。本仓主请求现在不带 `max_tokens`，厂商缺省的输出预算是未知数，而 DeepSeek 把 `max_tokens` 计入窗口（§3.2）。三家公开参照都把请求的输出预算算进了阈值：dsh 先扣「本次请求预留的输出」，报错信息直接要求把窗口配到高于请求实际生效的输出上限 [dsh] `packages/compaction/compaction-basic/src/config.ts:150`、`:172-178`；OpenCode 留出的余量同时给「压缩前的最后一次回复和摘要本身」[opencode] `packages/core/src/session/compaction.ts:129-136`；ZCode 把正常请求的输出上限带进压缩预留（至多按 21K 计），注释写明压缩必须与正常请求的输出目标对齐，否则「请求预算和压缩窗口会继续按两套常量计算」[zcode] `apps/zcode-cli/packages/core/src/compact/policy.ts:6-14`。
- **主请求按剩余窗口封顶**：`剩余 = hardLimit − 用量`；`0 < 剩余 < outputBase` 时请求带 `maxTokens = 剩余`；剩余不小于基线时照旧不带；剩余不为正数时也照旧不带——让端点报错、走错误恢复（本批的「到达硬线拒绝发送」落地后这条路径不再发出）。窗口未知时不封顶：按一个猜的窗口封顶会无故截断输出。缺省 128K 窗口上，压力线处的输出余量是 18.2K。做法同 [zcode] `apps/zcode-cli/packages/core/src/runtime/methods/model-token-limits.ts:17-41`（剩余 = 窗口 − 用量 − 1000，窗口未知不封顶，剩余非正保留基线走既有错误恢复），基线 32K 同 `:5-15`。与它的差别是本仓只在剩余不足基线时才带：采样证明 `max_tokens` 超过模型上限时三端点都报参数错（§3.2 第③类），字典缺输出上限的模型上固定带 32K 会让每一次请求都失败；只在需要时介入，其余请求的行为不变。代价要说清楚：不带时端点的缺省输出预算仍是未知数，I-14 在远离窗口时依赖「端点缺省不超过模型的输出上限」；不成立时的表现是第②类溢出报错，走 F-1。封顶值本身也可能超过模型的真实输出上限——字典缺 `maxOutputTokens` 的模型与自定义厂商都按 32K 基线封顶。这类第③类参数错由本仓的封顶引起，恢复 = 去掉封顶原步重发一次，并把报错里解析出的上限（三条原文都带上限，§3.2）记成该（厂商，模型）的观测输出上限；之后的封顶取 `剩余`、`outputBase`、观测输出上限三者最小。缺上限的规模：`packages/config-loader/src/models-dev-snapshot.json` 里 10194 个模型有 263 个缺输出上限、1430 个声明低于 32K。
- **封顶很小时的已知表现（F-14）**：开思考的模型会把很小的封顶全部用在思考上，正文为空、`finishReason: length`（§3.2）。它只出现在压力线与硬线之间——那里本来就是「压缩没能把用量压下去」的降级区。步照常结束，行上标明是输出被窗口截断，不重试。
- **摘要请求发送前先估**：`摘要输入 + summaryOut ≤ hardLimit` 才发，不满足先降档（§4.6）。压力线上恰好满足：用量 + 指令 + `summaryOut` 不超过上限 − 1.8K。预算不能直接取 `min(20_000, reserve)`——那样在缺省 128K 窗口上，压力线处的摘要是 108.8K + 指令 + 19.2K，超过 128K，在 DeepSeek 上第一发就 400。
- 15% 的来由：参照实现里三家的余量是窗口的 13–17%；OpenCode 选 15% 的依据是真实会话里单步增长的 p99 约 2.2 万 token [opencode] `packages/core/src/session/compaction.ts:130-136`。本仓估算每步被锚点校正，另有硬线，所以取同一档。

### 4.4 触发

| 触发         | 时机                                  | 行为                                                                                                                                                                           |
| ------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 压力（自动） | 每步请求前 `用量 ≥ pressure`          | 压缩后重新派生再发请求；选区判「历史不足」→ 跳过模型摘要，进 §4.9 第 2 步                                                                                                      |
| 溢出（兜底） | 请求失败且错误码是 `CONTEXT_OVERFLOW` | 压缩后**原步重发**（不新开 step、不计步数），最多一次；摘要自身失败或重发仍溢出 → 走 §4.9 的阶梯（无模型摘要超长步单元，落了账就照常重发）；阶梯也救不了才上报**原始溢出错误** |
| 手动         | 用户发起                              | 作为 `kind=compact` 队列意图入队（经输入框提交 `/compact`，D-092 修订）：空闲即消费；忙时排到队尾，回合结束后执行；重复请求拒绝（§4.10、D-092）                                |

压力阶段的压缩失败**不致命**：还没超硬线就照常发主请求，留一条可见警告（F-2）。只有已经超限时才致命。

溢出的那一次失败不落 `error` 行——原始错误记进 `compaction/start` 的 `cause`，只有最终放弃时才落（F-1）。否则一次已经被救回的溢出，会在对话里留下一条看着像失败的报错。

### 4.5 区间选择

- **单元**：同一个 `(turn, step)` 的 `assistant/message` + 它的 `tool/call` + `tool/result` 是一个单元；每条 `user/message` 自成一个单元。
- **尾部保留**：从最新往前收，直到估算量达到 `retain = clamp(floor(上限 × 0.12), 4_000, 32_000)`；最新的单元无论多大都整个保留。
- **头部**：尾部之前的全部单元。头部估算量不足 `max(4_000, 上限 × 0.05)` 时判「可压缩的历史不足」，跳过。
- **守卫**：区间不含任何 `system/message`；有在途调用的单元不进区间（「在途」= 属于当前仍在跑的回合且尚无结果；回合已结束的孤儿调用是崩溃遗留，结果永远不会再来、派生已合成错误结果，按已结算处理——否则一次中途崩溃就让选区永久判「不可压」）；起点严格大于上一次**模型摘要**区间与滚动记录的终点（session.md §4「区间只向前推进、不重叠」）。无模型摘要的替换区间不参与这条前推记账（它允许落在尾部、摘最新一步），只当截断点：新区间若跨越它，截到它之前，绝不允许重叠（store 先写生效、跨越即整条被拒）。
- **前沿与分段**（2026-11-26 复审）：落在上一次模型摘要终点之前的可见单元是「残留碎片」（被截断点挡下来的老历史），不能再进区间，也不参与起点计算；截断点（系统消息 / 无模型区间）把可压窗口切成若干连续段，**优先取最早一段**（先压老历史），该段不足 `headMin` 时取下一段。只从后往前截会让中段一次无模型摘要留下的短碎片把后面的历史永久挡死（§4.9 的「最新一步也能摘」允许摘中段大步）——这是 P1，见 §17。
- **滚动摘要**：上一次的摘要记录其 seq 落在新区间之内，随新区间一起退出表面；新摘要的提示词里带上旧摘要全文。这样摘要不会一份份累积。滚动下探只对最早一段、且记录 seq 与段首之间没有截断点时才做（下探区间会罩住截断点）。
  - 这需要给派生规则加一条修订：`plugins/session/src/derive.ts:45-53` 先处理替换标记、后判断是否被遮蔽，所以后到的区间罩不掉先前的摘要。修订 = 带替换标记的记录，自身 seq 落在更晚被接受的区间内时同样退出表面。**这是对 session.md §4 的修订，已取（§8），随本批落码时改 session.md。**

### 4.6 摘要请求

- **直接复用本步的主请求对象**：同 `messages`（请求前的派生快照）、同工具表、同 `reasoningEffort`、同会话头，只在末尾追加一条用户消息。主循环怎么发，摘要就怎么发——I-4 由构造保证，不靠约定。

**同形请求的可行区间**：`摘要输入 + 工具表 + 指令 + summaryOut ≤ hardLimit`（工具表与主请求同款，必须计入；漏算它，压力线上就可能超窗）。缺省 128K 上，压力线 108.8K、summaryOut 17.2K、硬线 127K，同形只装得下用量落在 108.8K～约 109.6K 的窄带——**约 800 token**。步边界上的用量由一步的增长量决定（通常几千），所以**第 1 档（头部前缀）是常规路径，不是兜底**；窗口越大窄带自然变宽（200K 约 9K、1M 约 43K）。参照实现算的是同一笔账：OpenCode 的 15% 里 16K 给摘要、其余吸收越过触发线的一步，窗口不到约 107K 时它自己承认「自动压缩永远走回退」[opencode] `packages/core/src/session/compaction.ts:129-135`、`:524-529`；dsh 的 64K 余量同样是从阈值里先扣掉的；ZCode 的 21K 输出预留 + 13K 缓冲让阈值处空出 34K。本仓不为此下调阈值：同形的收益只是摘要多看一段尾部，而尾部本身不被遮蔽、模型照样看得到它；代价却是每个会话多压一两次。

- 输出上限 `maxTokens = min(20_000, outputBase, hardLimit − 摘要输入估算)`，不低于预算 `summaryOut`（§4.3），给思考留余量。`outputBase` = min(声明输出上限, 观测输出上限)——R216 起与主循环封顶同源：第③类参数错学到的观测输出上限经 `ContextReading.outputBase` 随读数透出（meter 盖章），自动路径取 `PreStepValue.budget.outputBase`，手动路径经 `contextUsage()?.outputBase` 并入本地预算；都不在场时回退模型声明，均未声明 = 不加这一项（20K 帽仍在）。
- **摘要期出现的工具调用一律拒绝**：不执行、不落 `tool/call`，该次尝试判失败（智谱会无视禁止调用的约束）。
- **只有全部满足才算成功**：`finishReason` 是 `stop`、正文非空、没有工具调用、估算的摘要量小于被遮蔽量（I-7）。`length` 结束的摘要是被截断的，不当成功落账。
- **窗口小于 32K 的模型不做模型摘要**：`summaryOut` 在 16K 窗口上只剩 2 千、8K 上归零，思考模型会把这点预算全用在思考上（§3.2 的 F-14 形态）；这类模型直接走 §4.9 的无模型阶梯，到硬线拒绝。
- **发送前先估，不发必败的请求**（I-14）：`摘要输入 + summaryOut ≤ hardLimit` 才发。主请求已经超限的溢出路径上，同形的摘要请求必然同样超限；在会静默截断的端点上它不报错，被截掉的恰好是末尾的指令——模型收不到「写摘要」，成功判据却可能全部满足。所以不满足就先降档，不靠报错来发现。
- **四档**（每档先估后发；估得不准、厂商仍报溢出，就再降一档；四档用尽仍不满足即失败。第 1 档是常规路径，2–4 档按越线深度逐级启用）：
  1. 转写去掉尾部：只送头部 + 指令。尾部不被遮蔽，摘要不依赖它。
  2. 转写里的超长工具结果换成头尾摘录（无模型，§4.9 同款）。
  3. 头部只留后一半（按单元边界取整），提示词里注明「最早的 N 个轮次未纳入」。
  4. 头部只留后 35%。
- 第 3、4 档降的是转写，替换区间不变，仍覆盖整个头部：最早的那部分历史退出表面，却没有进摘要。未纳入的轮次数写在压缩行上，不只在提示词里。
- 缓存按档位说：第 1 档仍是主请求的前缀——系统提示、工具表与整个头部都命中（[opencode] 自己的注释也这么说：更短的前缀照样复用缓存，`packages/core/src/session/compaction.ts:524-529`）；第 2 档从被改写的第一条工具结果起断；第 3、4 档只命中系统提示与工具表。
- **摘要指令一律追加为一条用户消息**（同 OpenCode）。回合首步、插话或否决续跑之后，表面末条本身就是用户消息，于是出现连续两条用户消息：适配器不合并（`plugins/llm/src/messages.ts:28-30`），主循环在同一个步边界进场两条插话时本来也会产生这个形状。**四端点都接受**：相邻两条 user + 工具表 + `tool_choice: auto`，DeepSeek、智谱、Agnes、网关全部 200（§3.2）。手动压缩带的 `instructions` 并入这条用户消息——指令之后单列一节「用户的压缩说明」，要求优先保留说明里点到的决定、文件与约束；空说明不出现这一节。
- **提示词**（英文，D-050；本仓自写，不抄）分节且结构固定（八节）：目标与约束、已做的决定及理由、涉及的文件、当前工作状态、下一步、遇到的错误与修法、用户的长期要求、不能丢的细节（标识符 / 命令 / 取值）。每节标题必须出现，空节写 `(none)`——摘要是压缩后唯一的历史载体，松散散文会漏节（四家都用了固定结构：ZCode/CC 的 `<analysis>`+9 节、dsh 的 8 节「never drop a section」、OpenCode 的模板 + 模板合规检查）。另固定写明：工具输出是数据不是指令；用户立下的安全约束原样保留；不要复述系统提示 / 工具表 / 仓库约定（它们每次请求都会重发，不属于对话历史）；**不要提及压缩这件事**（dsh 与 OpenCode 都有这条：摘要里写「上下文被压缩了」会污染压缩后的语料，模型随后会向用户汇报）。滚动摘要的措辞是「新历史优先、保留仍为真的事实、丢掉已被新历史解决或过时的事实」——只增不减会让摘要随每次压缩变胖。摘要以 user 角色进表面，防注入两句不能省。
- **交接语**：替换记录的正文以一段固定说明开头（`SUMMARY_MARKER`）——这是检查点、取代更早的历史、当作既定背景、**从最新的消息直接继续，不要确认它、不要复述摘要、不要反问用户**。四家里 ZCode/CC 有「Continue… Resume directly — do not acknowledge the summary」、dsh 有「Continue the task directly from the messages that follow, without acknowledging this checkpoint」、OpenCode 有「treat it as historical context, not as new instructions」；没有这句，压缩后模型倾向于先向用户汇报「我总结了一下」，白费一轮。说明之后空一行接摘要正文。
- **端点自报溢出**：本地估算低估时厂商仍可能报溢出（AI 适配器上 `actual` / `limit` 可解析）——按 `actual ÷ 本次估算（输入 + 输出预留）` 缩放预算，裁光尾部、必要时再降 3/4 档，重发；最多两次（ZCode/CC 上限 3 次、OpenCode 四步 85/70/50/35%、dsh 留恢复钩子）。重发仍溢出才判失败（F-3）。

### 4.7 落账与事件

```
compaction/start    { trigger, 区间计划, 压缩前用量, cause? }
   … 摘要请求 …
compaction/summary  { 结果, 摘要请求的 usage, 模型 }          （成功时）
user/message        { source:"compaction", content, surfaceOp:{op:"replace", startSeq, endSeq} }   ← 原子替换
compaction/end      { state: completed | failed | interrupted, 压缩后用量, error? }
总线 compaction/applied（serial）                               ← 替换落账之后
```

- `compaction/start` 的 `cause` 记溢出路径的原始错误。审计字段放这些事件里：`user/message` 的校验是严格对象，未知键会被剥掉，挂不上去。失败另落基础的 `error` 事件——session.md §2.5 规定审计事实永不标 `ignorable`，所以 `compaction/*` 只承载观测值与界面状态，才有资格标 `ignorable: true`（旧读者回滚兼容）。
- **三个状态事件由 session 包注册为基础事件**（I-11）。先例是审批与提问事件：官方件的状态事件都是基础事件；而全仓非测试代码还没有任何插件注册过自有事件，投影器对插件自有事件也不投影。这样压缩行与悬挂 `start` 的收口都不依赖插件在不在。这一条修订 session.md §3 的官方事件计数（18 → 21）与 §4「插件自记 `compaction/*`」一句，已取（§8）。
- 审计事件先写、替换后写：崩溃在二者之间，审计说「摘要有」而表面没变——账本自洽，重放后就是没压缩。
- 替换事件的 `content` 以固定标记行开头（「以下是更早对话的摘要，它取代了之前的历史」），让模型认得这条消息的性质。
- **落账时机**：自动压缩的替换记录落在本步 `step/start` 之后、`request/header` 之前；溢出路径落在本步第一条 `request/header` 之后。session.md §4 现写的是「一次 `step/end` 之后、下一次 `step/start` 之前」，随本批修订（§8）。
- **中断与崩溃**：摘要途中被掐 → 写 `end{interrupted}`，不写替换；进程崩溃 → 什么都不写，或只留下悬挂的 `start`，或一条有 `summary` 却没有替换与 `end` 的半截记录。这些悬挂态都由投影器收口：重放时压缩行显示「已中断」，不补写账本事件——插件没有开档钩子，session 层的开档修理也不认识压缩事件。
- **`user/message` 的 `source` 是既有枚举**（`steer` / `veto` / `breaker` / 队列），本批新增 `compaction`（模型摘要）与 `compaction-digest`（无模型摘要）。标题派生取「首条用户消息」，三处都只排除了 `breaker`（`packages/protocol/src/session-title.ts:23`、`packages/server/src/session-registry.ts:539`、`packages/web/src/store.ts:138`）——必须改成排除全部合成来源，否则压缩记录可能成为会话标题。`compaction-digest` 的替换记录与 `compaction` 一样不投影成用户行，痕迹由压缩行承载（§4.9）。
- 追加替换后**核对返回事件的类型**（I-10）。
- `compaction/applied` 的监听器抛错不回灌：替换与 `end` 都已落账，压缩已经成立。监听器的异常落一条非致命 `error`，不让一次成功的压缩变成一步失败。

### 4.9 无模型兜底与超窗终局

单个工具结果有帽（2000 行 / 50KB），并行调用没有合计帽，一步就能涨过窗口（§3.1）。最新的几步工具结果本身就很大时，摘要救不了——被摘要遮蔽的只能是较早的历史，尾部还得留在表面里。阶梯有三个入口：压力路径的「历史不足，跳过」、压力路径的「到达硬线」、溢出路径的「摘要失败或重发仍溢出」。处理顺序固定为**先缩、再摘、最后才拒绝**：

1. 常规摘要（遮蔽头部）。
2. 仍高于压力线（溢出路径：仍装不下）：把工具结果超长的**整步单元**替换成一条简短的用户消息摘要（工具名 + 参数开头 + 结果头尾各留一段 + 省略字数），不调模型。「超长」= 该步单元的估算量超过 `max(4_000, 上限 × 0.05)`；在尾部还是在头部都算，按估算量从大到小处理——超长的那一步刚好落在尾部之外时，摘要请求自己也装不下它（§4.6 第 2 档用的就是这一手）。走的是同一个替换机制，不改「只有三种消息事件可带替换标记」的规则；替换记录的 `source` 用 `compaction-digest`，与模型摘要区分。
3. 仍到达硬线：拒绝发送，明确告诉用户为什么（F-6）。

无模型摘要让表面变小，本身就是可重发的结果——不必等模型摘要成功：溢出路径上只要替换落了账，就原步重发（同 dsh 的判据：表面替换代次前进即算有进展 [dsh] `packages/compaction/compaction-basic/src/index.ts:202-227`）。停止信号贯穿阶梯：已落的替换保留、未落的不再落，`end` 记 `interrupted`，中断不计失败（F-7）。

最新的一步同样可以摘——否则一次超大的工具输出就让会话永久卡在硬线上——但每一次替换都上屏，绝不静默丢弃；也永远不在失败时空转。替换记录的锚点是摘要正文：统计单元体积时必须跳过锚点，否则摘要正文会被算到被它遮蔽的旧单元头上，造出必被重叠裁决拒绝的幽灵候选（§17 第五轮）。

### 4.10 手动压缩

- **手动压缩是队列意图，不是旁路 RPC**（D-092，2026-11-27 对齐 [zcode] 的 `kind=compact` 输入意图）。它和普通消息共用同一条 FIFO（`queue.json` 持久化）与同一个消费点：`QueuedPrompt.kind = "compact"`，说明随条目持久化（`instructions`）。自动压缩仍不住队列——它是 `loop/pre-step` 的系统前置维护（[zcode] 同规：`autoCompactIsSystemTurnPrefix`），与手动压缩分开。
- `CompactionService.request({ instructions? })` 的受理：
  - 校验说明（≤ 2 000 码点，`trim()` 空按缺省）→ 重复检查：**已有压缩在跑或在队列里** → `rejected{reason:"compaction-in-progress"}`；压缩插件缺席 → `rejected{reason:"compaction-unavailable"}`。
  - 其余情况一律 `LoopService.enqueueCompact(instructions?)` 追加到队尾：队列空且冲刷链不在跑 → 入队即消费，响应 `accepted`；有回合在跑 / 队列非空 / 队列冻结 → 响应 `queued`。**不再有「下一步边界插队」的私有待办**——中途请求的压缩严格排在已有消息之后，回合结束后才执行。
  - 中断冻结（`queuePaused`）时只入队、不启动；由「继续发送」按 FIFO 恢复（[zcode] F03 同规）。
  - 可压缩的历史不足 → 消费时跳过，不占队列、不留压缩行。**消费时才知道的结果走活态，不走受理响应**（受理响应只有 `accepted` / `queued` / `rejected`）：插件广播 `compaction/skipped { id, reason: "history-insufficient" }`（活态，不落账本），宿主并入 `SessionState.compactionNotice`，输入栏按 `id` 变化提示一次「可压缩的历史不足，无需压缩」；下一次压缩开始即清、**切会话即收**（回执属会话，不跟人走——2026-11-27 用户纠偏：旧实现切走不清，提示跟着到别的会话），快照里带来的旧回执不重放。首版落码漏了这条通道——`skipped` 只写在受理响应的类型里、服务端从不返回，用户发完 `/compact` 草稿清空、什么都不发生（真浏览器 e2e 抓出）。
- **消费**：队列冲刷链取到队头 `kind=compact` 时，交给压缩插件注册的 worker（`LoopService.registerCompactWorker`）执行，`turn` 用维护 id（`m-…`）、不包回合、不挂回合头；`withActive("manual")` 保持压缩活态可停止。
  - worker 返回 `completed` / `skipped` → 队列继续冲刷下一条。
  - 返回 `failed` / `interrupted` → 剩余条目**原位冻结**（`queuePaused = true`），等「继续发送」显式恢复（[zcode] F07/F09：压缩失败或被停止后，后续队列不自动消费）。
  - 压缩插件缺席（例如持久队列来自启用过压缩件的会话）→ 队头 compact 项丢弃并广播，不把队列悬死。
- 手动压缩不受熔断限制，成功即解除熔断。
- 手动压缩的模型口径：取最近一条 `request/header` 里的模型（摘要请求会把整段表面发给它，不能落到另一家）；没有历史或该模型已不可解析才回落全局默认。REST / SDK 不带模型参数。
- 手动压缩的预算口径：模型声明窗口与计量器学到的观测上限（`contextUsage().size`）取小，静默截断端点上不按声明窗口硬发；上限 < 32K 时与自动路径同规——不做模型摘要，直接走 §4.9 的无模型阶梯（发必败的摘要请求没有意义）。
- 入口 = **输入框**（D-092 修订，2026-11-27）：手动压缩只有一个提交形状——输入框里的一行 `/compact [说明]`。余量面板的「压缩」与熔断横幅的「重试」只把 `/compact` 交给输入框（宿主门面 `prefill({ text })`，本批接线——D-085 起的空实现：只回填不发送；草稿为空才回填并聚焦，已有草稿不覆盖，面板就地提示），**不自己发**；用户在输入框点发送（或回车），走与消息同一个 `ComposerApi.submit()`——首词 `/compact`（去首尾空白后取首词，大小写不敏感；正文里出现的 `/compact` 不是命令）识别为压缩意图，其后为说明（可空，说明并入摘要指令，空说明直接压），经 SDK `compact()` → REST `POST /api/sessions/:id/compact` 入队；其余草稿照旧经 `prompt()`。提交结果在输入栏行内呈现：`accepted` / `queued` 清空草稿（进度看排队卡与压缩行）；`rejected`（已有压缩在跑或在排队 / 插件缺席）/ 请求失败 → 草稿回填 + 行内原因，不静默清空；历史不足在**消费时**被跳过 → 活态 `compaction/skipped` → `SessionState.compactionNotice` → 行内说明、不回填（见下条）。REST 响应 `{ state: "accepted" | "queued" | "skipped" | "rejected", reason? }`——`skipped` 只为契约兼容保留，官方服务端不返回；`rejected` 带 `reason`，其余不带。说明长度上限 2 000 码点（与 `summaryOut` 里留给指令的 2 千同一量级，超出部分由发送前估算的降档兜住）——界面提交前同上限校验（超限不提交、草稿保留 + 行内原因），REST 超限 400。REST 请求体 `{ instructions? }`（`trim()` 后空串按缺省处理），SDK 门面方法 server 与 SDK runtime 两套宿主面同一校验。说明计入摘要请求的输入，受 §4.6 的发送前估算约束。
- **slash 命令只接 `/compact` 一条**：输入框命令机制整体尚未定稿（清单里明确「定稿前命令部分不动工」），本条为首词解析的最小落地，不做命令菜单、补全，也不接其余命令。`/compact` 不是入口糖——它就是手动压缩的提交形状：按钮、横幅、手敲三处入口汇到同一个 `submit()`，提交、准入、排队、消费才真正与「发一条消息」同路；入口分叉成旁路按钮时，「同一条队列」只对了一半。

### 4.11 界面

- **压缩行**（新增 `Row` 种类 `compaction`）：画成分隔线，不是气泡——四家都是一行标记（§1.1「压缩处的可见行」）。行上：触发因（自动 / 手动）、状态（进行中 / 完成 / 失败 / 已中断）、压缩前后用量、所用模型；失败时带错误码与可行动的说明；未纳入摘要的轮次数、被无模型摘要的步单元数同样写在行上。摘要正文默认折叠、可展开（dsh 与闭源产品同款）；展开区走宿主 `renderMarkdown` 渲染成预览（与正文同一套 `.henira-md` 排版），限高内滚（360px），不提供原文/复制原文入口（2026-11-27 用户拍板，见 D-093）。`user/message{source:"compaction"}` 不再投影成用户气泡。
- **压缩行与回合的折叠**（随回合折叠，同 ZCode 的「助手工作」组）：
  - 回合中途的压缩行是这一回合工作的一部分，随「已工作」一起收起，在组里单独占一格（不与助手行、工具行合并）。
  - 本仓的折叠判据要显式接纳它：`plugins/web-ui/src/parts/conversation/turn-items.ts:169` 现在只认助手行与工具行，不接纳的话含压缩行的回合永远折不起来。
  - 压缩失败另落的那条非致命 `error` 行不进回合正文——与审批、提问的痕迹行同一处理（`plugins/web-ui/src/parts/conversation/turn-items.ts:146`）。痕迹由压缩行承载；进了正文既重复，又因为同文件 `:153-155` 把含 error 行的回合判成异常而破坏折叠。
  - 闲时的手动压缩只有一条压缩行、不挂回合头——现状已成立（`plugins/web-ui/src/parts/conversation/turn.tsx:71` 只在回合有计时或被中断时才显示回合头），不改。
- **进行中的压缩**：可停止（停止 = 中断，写 `end{interrupted}`，同 ZCode 的可停止活动）；期间不显示通用的「仍在等待模型响应」。停止入口 = 输入栏的停止钮（`LoopService` 增加对在途手动压缩的停止路径）。**停止只中断在途压缩**——队列里的条目是用户意图，原样保留并冻结（`queuePaused`），不随停止撤销（D-092 取代旧「停止 = 全停」）。
- **提交反馈**（D-092 修订：入口在输入框，反馈随之搬进输入栏）：手动压缩入队后草稿清空，进度看排队卡——`/compact` 行（可删除、可「立即发送」，不可编辑——[zcode] `useComposerEditMode.ts:452` 同规）；重复请求被拒、未启用、请求失败 → 草稿回填 + 输入栏行内原因；历史不足在消费时被跳过 → 活态 `compaction/skipped` → `SessionState.compactionNotice`，输入栏行内说明、不回填（受理响应不带这个结果）。跳过与拒绝不留行——ZCode 的「无需」态在本仓是即时反馈，不是常驻标记。余量面板在「有压缩已排队」时显示排队态、不再给入口；输入框已有草稿时点「压缩」不覆盖，面板就地提示先发送或清空。
- **上下文余量**：`SessionState.context { used, size, pressure, estimated, cacheHitRate, parts }`（`size` = 上限；`parts` = `{ system, tools, messages }`，按整面估算的占比折算、恒为估算——`estimated` 只描述 `used`；三段按 `used` 折算后之和等于 `used`，舍入差额并入 `messages`，任一段不为负；`cacheHitRate` 见 §4.2，取不到就不带），loop 每步重算并广播 `context/changed`，宿主并入活态（与队列活态同一出口 `LoopService.contextUsage()`）。输入栏工具排右侧一个常驻圆环入口（14px，圆环进度 = `used ÷ size`，栏内不放数字；完整读数在面板头、`aria-label` 与 tooltip 里；形态同 [zcode] `packages/ui/src/components/ai-elements/context.tsx:74-110`），悬停展开（指针移入面板不收起；触屏与键盘用点击开合）：精确读数还是估算、三段构成条（系统提示 / 工具表 / 消息——**段宽按上限 `size` 折算**，条 = 占用 + 构成二合一：63% 用量渲染 63% 宽、余下是可见空轨道；2026-11-27 用户纠偏——旧实现段宽按 `used` 折算恒满格，用量不进条的几何，肉眼读作「没有刻度」）、距压力线还剩多少、缓存命中率（低于 78% 不显示）；预警区间圆环转警示色（本批补 `--henira-warning-text` / `--henira-warning-bg` 两个 token，现有 token 只有 accent / danger）；用量为 0 或非法时不渲染（同 ZCode：`packages/ui/src/chat-input-toolbar/contextUsage.tsx:83`、`:216-235`）。
- **重启恢复**（2026-11-27 补）：余量读数不落账本，但重启后打开历史会话要能显示——未装配的磁盘快照路径按账本恢复（`restoreContextReading`：最近一条 `request/header` 的模型 + 锚点 `step/end.usage` + 锚后表面估算；工具表体积用锚点 `input` 减去系统/消息反推），恢复读数带 `partial` 标记，界面隐藏三段明细、只显示总量与剩余；会话挂载后 loop 的 `restoreContext()` 按真实工具表重算并广播，转为完整形态。**锚点被替换记录作废时**（空闲手动压缩后重启：最近一条 `step/end.usage` 落在压缩之前——2026-11-27 活体验收发现的第二个缺口），从最近一次成功压缩的 `compaction/end.after` 重新起算（该值是压缩后的整面估算、含当时的真实工具表），叠加替换记录之后新增表面的估算；读数同样带 `estimated` 与 `partial`，重启即显示，不再等下一条消息。替换之后没有成功 `compaction/end`（崩溃窗口）保持缺省——不猜。**fork 子会话装配后同样补跑一次 `restoreContext()`**（此前只挂在懒挂载 `#attach` 上，fork 出来的会话余量圆环要等下一句消息才出现——同日活体验收发现的第一个缺口），投影补账与悬挂压缩收口同 `#attach` 同款。从未请求过的会话没有 header / 锚点，读数保持缺省（入口不显示，不猜）。三家参照都把最近一次响应 usage 随会话记录持久化、重启后直接显示（[zcode] `message-history-usage.ts` 的 `persistedTokenUsageBaseline`、[opencode] `contextUsage()` 的 `lastAssistantWithUsage`、[dsh] token-meter 的 `pressureTokens` / `projectedTokens` 投影）。
- **溢出错误的呈现**：`CONTEXT_OVERFLOW` 错误行翻成可行动中文——请求了多少 token、上限多少（从报错解析，解析不出就不带数字）、现在该怎么办；英文原文折叠保留。
- **预警**：`used` 进入压力线下方 10% 窗口（`used ≥ pressure − floor(size × 0.10)`）时出提示，写明「距自动压缩还差 N%」，`N = max(0, floor((pressure − used) ÷ size × 100))`，`N` 为 0 时写「下一步请求前自动压缩」（同闭源产品的「N% until auto-compact」）；压缩失败且余量仍高出警告行；熔断出常驻横幅。
- **压缩期间不再显示通用的「仍在等待模型响应」**。
- 文案全部进 `plugins/web-ui/src/locales/zh.ts`；失败码逐个有可行动的中文（现在只有空闲超时一个码有）。

## 6. 落码顺序

四层是依赖顺序，不是四个交付版本：**对外一次交齐**。层与层之间先跑门禁与自测（后一层依赖前一层的行为），但不提交、不推送半成品；全部落地后七门禁逐条跑一遍 + 真 key 全链验收（§7）、一次文档同步与 ADR，一笔入册。层的边界就是定位边界——出了错按层归因，不靠提交历史。

1. **地基**（先落地、可单独验收，不单独交付）：`step/end.usage` 五字段落账；`toLlmError` 补状态与响应体；溢出分类（`max_tokens` 参数错单列成 `OUTPUT_LIMIT_EXCEEDED`，不判溢出）；关掉 SDK 的缺省错误打印；派发 `loop/pre-step`（载荷带读数）；计量器（住 loop，估算函数与阈值公式进 protocol）+ 余量上屏；溢出错误翻成可行动中文；主请求按剩余窗口封顶输出（封顶引起的第③类：去掉封顶重发一次并记下观测输出上限）。估算系数已用真实账本定标（§4.2）。这一层做完，溢出从一条看不懂的英文错误变成「看得见的余量 + 认得出的溢出」。
2. **压缩主体**：压力触发、选区、摘要请求、原子替换、滚动摘要的派生修订、压缩行、正在压缩状态、`compaction/applied`。
3. **失败语义**：溢出后重发（`loop/request-failed`）、摘要装不下时的预算检查与降档、熔断、无模型兜底、超窗终局、截断嫌疑、§4.9 阶梯的三个入口。
4. **手动压缩**：入口（输入框 `/compact`——面板按钮 / 横幅只交草稿，D-092 修订）、REST / SDK、与消息同队列。

**P2（已修）**

**P3（只报不修，留在 §8/§9 的账上）**
