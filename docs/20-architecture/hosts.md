## 1. 总纲：引擎是库，宿主决定它住哪

引擎（kernel + 插件）是**库**——不知道 HTTP、不画界面、不占端口。每个**宿主**负责把引擎装配起来，并决定它住哪。Henira 没有"必须先起服务端"这一层，server 只是宿主之一。

三种拓扑：

```
① 一对多：多个客户端 ──→ 一个 server 进程（引擎装配在内）
② 一对一：客户端 ──→ 自带的私有 server（仍是 C/S，只是私有）
③ 零服务：你的程序 ──直接调用──→ 引擎（进程内嵌：无 server、无端口、无 HTTP）
```

②是①的私有化用法，不单列为目标形态；有意义的区分是①与③。

**为什么不是"必须先起服务"**：headless / sdk / 脚本场景先起一个 server 纯属负担（无服务、无端口、一次性任务，dsh headless 同款：`packages/bundle/headless/README.zh.md:12`）；桌面 / Web 的多客户端形态则天然要服务。所以 **Henira ①③并存**——桌面 / Web 住①，headless / sdk / 脚本住③。①③用的是同一份引擎代码，只是住处不同。

## 3. 宿主契约

一个宿主要把引擎跑起来，必须提供四样（与 [packages.md](./packages.md)「槽位实现归属」一致）：

1. **配置注入**：经 config-loader 装配，并把 `ConfigService` 在启动时注入；
2. **InteractionService 实现**：由引擎所在进程的宿主实现（①=server，③=cli / sdk 嵌入方；sdk 自带缺省实现，归属细则见 [packages.md](./packages.md)「槽位实现归属」）；审批 / 提问的**收答面**按形态走——web 端 = 网页审批卡（server 实现、网页呈现与回答），cli / TUI = 终端问答，examples = mock 自动答；
3. **事件消费**：EventBus 的出口——server = SSE，sdk = 进程内订阅；
4. **输入投递**：prompt 怎么进来——HTTP 端点 / SDK 调用 / 输入框。

**桌面的特殊性**：desktop 宿主不自己实现这四样——它复用 server（①）与 web（界面），本体只是薄壳（§4）。这是 A1 的本质：不新增第四种实现，不新增协议。

**进程与会话的划分（定稿 · 2026-11-13）**：①宿主 = 进程级壳 + **每会话一个 harness 实例**（装配三步每会话执行，D-016 即此语义；SlotMap 各槽位服务随会话实例生灭——`InteractionService.listPending()` 不带会话号，正因为每会话一份）。进程级共享：HTTP / SSE、server.json 握手、设置缓存，**MCP 连接管理器进程级一份**（plugin-mcp 内部实现，工具注入各会话注册表）。并发：每会话同时一个回合在跑，跨会话无上限。实证同构：ZCode"一个 App = 一个运行时 = 一个 sessionId"（`dynamic-workflow-run-progress-sink.ts:27`）、OpenCode 按目录隔离实例（`location-services.ts:14-125`）。③零服务宿主天然单会话，不涉及。

## 4. 桌面（Electron）＝ A1（D-035）

- 主进程用 **utilityProcess**（Electron 受管子进程，应用退出自动回收、无孤儿）拉起 server 包——与 `henira serve` 同一份代码；
- 窗口加载 `http://127.0.0.1:<随机端口>`，同源伺服 web 构建，**界面与 server 零改动**；
- **握手与防双开**：server 落 server.json（端口等）；后启实例读到已活 → 只开新窗口（单一实例锁 + 握手文件的通行做法）；
- **崩溃隔离**：引擎死 = 子进程死，窗口活着、可提示重启；
- **回环三件套**（server 诞生日起生效，M3）：
  1. 默认只绑 `127.0.0.1`（对公网 / 局域网开放 = 显式配置，属自托管 / 云端场景）；
  2. 随机端口；
  3. Host / Origin 头校验（防恶意网页把域名解析到 127.0.0.1 冒充访问本机服务），并预留可选 token 位；
- **排期**：中远期，不阻塞 M1–M4——`henira serve` + 浏览器 M3 即可用，桌面只是它的壳（托盘 / 自动更新 / 防双开等系统能力）。

**被放弃**：A2（引擎进主进程 + IPC）——web 界面永久双轨（HTTP+SSE 与 IPC 两套通信实现都要写、都要测）；A3（主进程内嵌 + 进程内回环 server）——省一个进程，但失崩溃隔离，且 `henira serve` 反正保留、"server 作为独立进程"的代码路径已存在，A3 实际省不下东西。
**重开条件**：出现"禁止本机监听端口"的部署硬约束 → A2；强制单进程 → A3。

## 5. 云端＝分层丙案（D-036）

云端 = 把 server + 引擎放进每用户一个的容器（隔离小箱子），用户拿浏览器隔公网连。与本地相比只差四样，各有归宿：

| 差什么                 | 本质                   | 归宿                                                                                 |
| ---------------------- | ---------------------- | ------------------------------------------------------------------------------------ |
| 验钥匙（鉴权 token）   | 协议的一部分           | **server**（三件套已预留位）                                                         |
| 会话 user 字段（归属） | 数据模型的一部分       | **protocol / session**，一个字段（已落 SessionHeader 可选 `user?`，session.md §2.1） |
| 容器生灭（编排）       | 运维机器，不是功能代码 | **`examples/cloud` 部署样例**（docker-compose），不进任何代码包                      |
| HTTPS（加密）          | 传输层                 | 前置代理（nginx / Caddy 等），零代码                                                 |

要点：

- **不立 `@henira/cloud` 宿主包**：一份协议本地云端通吃（远程 client 一个 `createClient({ baseUrl, token })` 即可）；且"宿主互不依赖"规则（packages.md 规则 3）下，cloud 宿主想复用 HTTP 层还得先抽公共库——预交税。**重开条件**：云端真出现与本地不同的协议需求（换流式通道 / 计费接口）再立包；
- **一人一容器一进程、每用户一个卷**（容器即隔离单位，编排是运维不是协议）；
- **云容器本身即沙箱**：云端不需要沙箱插件；沙箱插件是本地执行的事（packages.md 外圈，设计待定，与云不共用机制）；
- 商业化机器（账号注册 / 计费）在开源仓库外；
- 默认仍只绑回环（D-035 三件套）；对公网开放是自托管 / 云端部署时的显式配置。

## 6. 待定与倾向（50-open 🟢）

- **TUI**——倾向 **C1 薄客户端连①**：终端里"不起服务"的坑位已由发布后 cli 聊天占住（进程内嵌③的单发 / Repl）；TUI 全屏走 C1 复用整个①栈（协议 / 审批 / 会话），C2 等于把引擎装配再背一遍。共同成本 = InteractionService 终端实现。发布后按需求定稿；
- **移动端层次**——倾向 **远程客户端先行**：复用整个①栈（web 做响应式 + 远程协议 + D-035 token 位），第一步可为响应式网页 / PWA，原生壳后置；手机本地执行（proot 类方案冷启动慢）是执行环境课题不是界面课题，单独立项。移动 UI 词表已随 D-033 推迟。发布后按需求定稿；
- **本地沙箱插件**——倾向 **暂缓 + 容器过渡**：需要新槽位（SandboxService）→ 动骨架 → 开工时才立 ADR（packages.md 规则 6）；云端已有容器隔离（D-036）。**过渡答案现在就有**：把 `henira serve` 整只跑进容器 / devcontainer（项目目录挂进去）即得隔离——插件将来做的是"方便"，不是"能力从无到有"。与云不共用机制（D-036 已定）。
